# Native service booking and waiting-list controls

The native service catalogue now includes a per-service booking panel when the existing approved native Test session integration is supplied. Without it, the website handoff remains. The panel loads current public policy/price and future slots alongside an authenticated personal dashboard. Merely opening a card never sends a mutation. Current price, cancellation/rescheduling policy, refund percentages, late-charge disclosure and offer expiry are displayed before explicit confirmation. Final service availability and terms remain server/database authority.

New-booking commands contain only a returned slot and the reviewed expected price, INR currency and normalized policy, using the existing `book` API. The existing account header and native bearer session bind every mutation. Acknowledgements alone do not establish success: a refreshed owner-bound, non-truncated dashboard must show exactly one matching active booking with the expected ID (when acknowledged), slot, service, time, price, currency and policy. No payment is processed.

Waiting-list join uses an explicitly displayed future 14-day window. Existing waiting/offered entries prevent another join and can be left through confirmation. Join/leave is verified in fresh owner-scoped records. If another device concurrently creates an entry with different terms/window, the panel remains unconfirmed rather than claiming that the new window was saved. Joining is not a booking and never accepts an offer. Offer acceptance/decline remains online for this milestone.

Known rejections require new current terms. Lost responses, malformed acknowledgements, mismatched records or incomplete dashboards cannot be retried automatically. Only reconciliation reads are available for uncertain writes. Account changes, service/session replacement, backgrounding and unmounting clear private UI state and invalidate late responses. Tokens are never stored in rendered state. A truncated dashboard blocks this workflow rather than treating a partial list as complete.

Tests cover the real shared HTTP command transport and actual TSX component interaction using fixtures: explicit booking and waitlist confirmation, same-account headers, reviewed price/policy, one dispatch on repeated taps, join/leave confirmation, malformed/changed results, account switching, duplicate slots, missing history and lost writes. The existing network-isolated PostgreSQL suite covers allocation concurrency, current terms, cancellation, successful/failed rescheduling, rollback, daycare resource isolation and waitlist FIFO/expiry. These checks do not claim physical-device or hosted acceptance.

Existing cancellation/rescheduling, notification feed and public website workflows are preserved. Existing SQL continues to record appointment notifications; no email/SMS/push transport, notification worker, webhook, provider credential, payment or hosted scheduler was enabled. A delivery adapter and independently verified sandbox provider integration remain future work. Native offer acceptance, device/store acceptance, remaining dependency advisories and explicitly approved hosted migrations/integration validation are launch blockers. No dependency/configuration upgrade or live database change occurred.
