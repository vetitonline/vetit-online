# Native waiting-list offers and appointment notification read state

The existing native service booking panel now reviews, accepts and declines waiting-list offers. The panel joins an offer to the current customer's active offered entry for the displayed service and validates identity, slot, currency, amount, policy and timestamps. Foreign, expired or unlisted offers cannot be submitted. It displays the saved offer price, policy, times and expiry before explicit confirmation; it does not silently replace offer terms with newer public terms. PostgreSQL still rejects expiry, lost capacity or price drift; reviewing a snapshot does not bypass current backend checks.

Acceptance uses the existing `acceptOffer` command with the verified account header and bearer session. An acknowledgement alone is insufficient: a fresh, complete personal dashboard must link the accepted offer to the matching booking and accepted waitlist entry. Slot, service, time, policy, amount and currency must all match the reviewed snapshot. Decline likewise requires an explicitly declined offer and left entry. Unknown results allow reconciliation reads only, never an automatic second acceptance. Backgrounding, source changes and sign-out invalidate private state. No charge or refund is performed.

The account appointment feed now shows read/unread state and a confirmed “mark notification read” control. It reuses the existing appointment action controller and `readNotification` API. Only a returned personal notification can be selected, provider views cannot mark personal records, and the refreshed projection must show the notification read before success. The feed continues to exclude raw notification payloads. No email, SMS, push provider, webhook, notification permission, delivery worker or hosted scheduler was added or enabled.

Validation covers actual TSX interactions with mock transport, saved/current price differences, expiry during review, foreign IDs, linked booking evidence, lost acknowledgements, account switches and readback. The isolated PostgreSQL suite verifies offer allocation/FIFO, accepted price/policy preservation (including the booking's market metadata), decline handoff, recipient-only idempotent notification reads and an entirely disabled delivery outbox. Tests explicitly leave their prior synthetic waiting entries before creating a new FIFO scenario, preserving history rather than deleting fixtures.

This milestone changes no database schema, hosted state, credentials or dependency versions. Remaining launch gates are approved hosted migrations and Auth/RLS acceptance, provider sandbox/live integration approval, notification delivery and operational monitoring, physical Android/iOS/store acceptance, refund operations and remaining dependency advisories. Existing booking, cancellation, rescheduling, waitlist join/leave, checkout and admin work are preserved. This is an isolated acceptance checkpoint, not production activation.
