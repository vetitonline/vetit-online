# Native customer rescheduling

Native customer appointments now expose eligible rescheduling through the existing action controller. Cancellation and provider actions retain their existing flow. No backend schema, credential, dependency version or hosted configuration changed.

The customer chooses “Reschedule appointment”, loads public replacement availability for the same service from the existing 14-day API, selects a returned slot, reviews its exact India-local time and the retained-price notice, then explicitly confirms. No new action is sent merely by opening or choosing availability. Missing policy, expired notice windows, stale revisions, provider scope, invalid/duplicate slot responses and unlisted selections fail closed. Empty availability cannot enable a command. Reads are bounded, abortable and invalidated by account changes, backgrounding, disposal or backing out.

The command reuses the authenticated appointment API with the displayed booking revision and account precondition. PostgreSQL remains final authority for ownership, saved policy, replacement service/location/resource and concurrent allocation. A returned booking ID is an acknowledgement, not success: the refreshed booking must have a higher revision, the chosen slot and time interval, and unchanged service, currency, agreed price and booking status. Unknown write results require reconciliation and are never automatically retried. Changing the service, price or allocation in refreshed data cannot produce a successful UI acknowledgement.

Tests include actual native-component interaction, policy/revision checks, malformed availability, explicit confirmation, preserved-price/service verification, account switching, late availability responses and lost acknowledgements. The existing disposable PostgreSQL suite independently tests successful/failed rescheduling, rollback, concurrent revisions, cancellation, daycare resource isolation, waitlist FIFO and expiry. Test infrastructure is local and network-isolated; no hosted database is modified.

The native notification feed remains read-only and excludes payloads. No notification sender, live provider, refund, payment, webhook or scheduler was activated. Real provider adapters still need independently verified sandbox evidence and bounded/idempotent calls under the existing server-only interfaces. Native new-booking and waitlist controls remain future work; the website retains those existing workflows. Physical Android/iOS acceptance, compatible remediation of remaining transitive advisories, provider sandbox integration and explicitly approved hosted migration/acceptance are still required before launch. Dependency major upgrades were not attempted.
