# Vetit Online mobile foundation

This standalone Expo/React Native app consumes the existing read-only `GET /api/catalog` endpoint through the shared client at `../src/lib/marketplace/catalog-client.js`, and published service discovery through `GET/POST /api/services` using `../src/lib/services/service-client.js`. These views use the web API. Optional native authentication uses the separately approved injected SDK/storage composition described below; no credentials are embedded in the app source.

Service filters use the shared city, locality, postcode, category and country-code contract. Location-based searches send latitude/longitude in a same-origin `POST` body rather than putting coordinates in a URL; the API returns a rounded distance and never returns provider coordinates. The mobile screen currently supports city/postcode search and links to the website for browser permission-based device location. A native location permission flow needs an approved Expo location module before it can be added.

## Run locally

This Test candidate requires **both** `EXPO_PUBLIC_VETIT_API_BASE_URL` and `EXPO_PUBLIC_VETIT_TEST_API_ORIGIN`, set to the same explicitly approved Test web origin in every build mode. Missing/mismatched origins and `vetit.online` (including subdomains) fail closed. Localhost/private LAN HTTP is permitted for local device/emulator development; remote Test origins require HTTPS. The web server must use `PUBLIC_SUPABASE_URL=https://apfyfmokcynqiaxqvvxx.supabase.co` and the existing Test publishable key, including during builds/previews. Never copy a secret/service-role key into public variables. Actual credential/environment files were not changed.

Install only this standalone package with `pnpm -C mobile install --ignore-workspace`, copy `.env.example` to `.env`, then run `pnpm -C mobile start` and `pnpm -C mobile typecheck`. The `--ignore-workspace` flag is needed because the root pnpm workspace is dedicated to the web app; it keeps the mobile dependency graph separate. Set both endpoint variables to the approved Astro Test server origin. A physical phone must use a host-reachable LAN address; Android emulators commonly use `http://10.0.2.2:<port>`. Production release configuration requires separate approval and is outside this Test candidate.

The app uses public catalogue and service APIs for browsing. The in-memory basket is a preview: it is not synced, persisted, submitted as an order, or connected to payment. Web and mobile use the shared appointment API client to view public future slots; it does not create a booking. The approved injected native session also supports the read-only views described below. Hosted booking, saved addresses, persistent carts and order creation still require coordinated backend integration. Default preview handoffs and prepared native auth/reviewer components are not certification of real hosted authentication or authorisation.

`metro.config.js` exposes the shared repository contracts and original logo to Expo while excluding the web dependency cache and generated builds. Reuse the installed dependencies for validation. Android/iOS JavaScript export is a bundle check; it does not certify Hermes bytecode, an installable app, simulator/device rendering, protected OS storage or hosted sign-in.

Appointment lifecycle contracts live in `src/lib/services/appointment-lifecycle*.js`. The native view supports personal/provider reads and explicit provider booking confirmation, completion and cancellation through the existing API when a verified native Test session and coordinated runtime are available. Customer booking/cancellation/rescheduling and provider slot/policy editing continue through the authenticated web page `/appointments`. Lifecycle RPCs remain proposal-only until separately approved and installed; missing RPCs report unavailable. Initial provider terms allow free changes until 24 hours before the appointment and expire waiting-list offers after 15 minutes. Email/push outbox entries remain disabled and refunds require review.
# Native moderation session and queue integration (local candidate)

The prepared `createSecureNativeModeration` composition now accepts the existing Supabase `createClient` factory, exact Test URL/publishable key, approved OS-protected storage and a cryptographic UUID source. It refuses construction without explicit Test-auth/storage/crypto approval. It never constructs a live client by default. No SecureStore/Crypto package is installed or bound in this checkpoint; there is no plain-storage fallback.

`NativeSignIn` provides optional English/Hindi email-code UI for existing accounts only. The adapter forbids signup and arbitrary redirect options, disables URL session ingestion/background refresh, namespaces protected storage and returns tokens only for server verification. Email/code input is transient; raw SDK errors are hidden. Sign-out is device-scoped and blocks local reuse even when confirmation fails; it does not claim global JWT revocation. Adapter operations time out after at most ten seconds and cannot restore local access after timeout, sign-out or disposal. Initial/token-refresh events do not falsely establish identity.

Pass the approved composition as the existing App `nativeModeration` prop; it supplies auth, session, client and requestId. Its dispose method removes the auth listener and clears private verification state. Construct it once outside render after approval. Real OTP delivery, protected OS storage, mobile bundling/device rendering and real Test sign-in remain unverified. Current preview behavior remains unchanged without that injected composition.

`NativeModeration` is wired into the account tab through the optional `nativeModeration` App prop. Create its client with `createMobileModerationClient`, its session host with `createNativeModerationSession`, and provide a platform cryptographic UUID generator. Both factories require explicit matching Test API origins and reject production. No credential goes in a URL or public environment variable.

The platform auth adapter must supply `getAccessToken()` from its approved secure storage. The host verifies that token through `/api/moderation-session`; it does not decode JWT claims locally. Subscription snapshots contain only verified user ID and a reviewer presentation hint. Queue and decision authorization still require current server/database permissions. Verification is deduplicated and bounded to ten seconds, including token acquisition. Token rotation and background/disconnect invalidate pending responses.

The native queue supports bounded cursor paging, refresh, empty/error/denied states, flagged-case triage, case details and return navigation. Web/native share review-routing rules. Eligible automatic decisions are status-only; uncertain, blocked, escalated or policy-manual screened cases expose authorised review actions. Automatic publication is still disabled. Global Test reviewer scope requires explicit approval.

The default Expo preview retains the web sign-in handoff because no approved native secure-token/auth bootstrap adapter or crypto UUID source is configured here. These are injected dependencies, not fake successful sign-in. On actual logout, the platform auth owner must clear/revoke its session as appropriate and call `session.clear()`. Background clearing only removes local verification/private UI; it does not sign out or revoke hosted sessions.

Local tests cover verified identity, lifecycle races/timeouts, cursor/DTO validation and actual routes over bounded loopback HTTP with synthetic auth/RPC. Android SDK tools and a native renderer are not available locally; device rendering and real Test authentication remain unverified. Do not activate providers or hosted automation during local integration.

## Native appointment and provider schedule review

With the existing approved `nativeModeration` session injected, the account tab now includes a native appointment view. It reads personal bookings and lets an authorised owner/admin select a returned provider business to review its bookings, service titles and schedule. Reads use the existing `/api/appointments` contract, verified bearer identity, no cookies/redirects, bounded rows and a ten-second deadline covering authentication and transport. Private raw rows, customer identifiers and tokens are excluded from view snapshots. Backgrounding, account changes, configuration changes and disposal invalidate pending work and clear the view.

Times are explicitly labelled Asia/Kolkata. English is the default; Hindi copy and the shared scheduled-language/script resolver provide extensible fallback for other Indian languages. Unreviewed translations fall back to English. Provider booking actions require an additional confirmation showing the action, service and time. They send the displayed revision and reverify identity; completion is offered only for a finished confirmed booking. Raw customer records and tokens are excluded from action snapshots.

Writes are never retried automatically. A conflict requires a fresh read and new confirmation. An uncertain outcome blocks further actions until a refreshed booking resolves it through its status and advanced revision. Cancellation explicitly warns that any refund needs review; no refund/charge command is generated. Account changes/backgrounding clear private action state and require fresh view data; backend revision checks remain necessary across remounts because there is no persistent native write journal. Missing/unapproved RPCs report unavailable. These controls neither activate a hosted SQL candidate nor grant provider permission.

Run `pnpm test:native-appointments` for read coverage and `pnpm test:native-provider-appointments` for provider action plus affected read coverage. Actual browser, device and hosted-session results are recorded separately in the latest development/provider-action reports.
